# 규칙 파일 종합 분석 및 검증

## 📋 개요

모든 규칙 파일(`agent.mdc`, `docs.mdc`, `plan.mdc`, `prd.mdc`, `tasks.mdc`)을 종합적으로 검토하여 프로젝트 진행 시 발생할 수 있는 문제점, 충돌, 모호한 부분을 분석합니다.

**작성일**: 2025-01-01

---

## ✅ 일관성 있는 부분

### 1. Phase 번호 체계
- **모든 규칙 파일에서 일관됨**: `Phase N` (메인 Phase), `N-M` (Sub-task, 하이픈 사용)
- **참조 위치**: `plan.mdc`의 "Phase 번호 체계" 섹션에 정의되어 있고, 다른 모든 규칙 파일에서 이를 참조

### 2. History 기록 형식
- **통일된 형식**: `plan.mdc`의 "History 기록 형식" 섹션에 통일된 형식 정의
- **모든 규칙 파일에서 참조**: `agent.mdc`, `docs.mdc`, `tasks.mdc` 모두 동일한 형식을 참조

### 3. 승인 프로세스
- **일관된 규칙**: `plan/plan.md`, `plan/prd.md`, `plan/tasks/` 수정 시 사용자 승인 필수
- **예외**: `docs/` 하위 파일은 승인 불필요 (모든 규칙 파일에서 일관됨)

### 4. 문서 역할 구분
- **명확한 구분**: `docs/`와 `plan/tasks/`의 역할이 명확히 구분됨
- **참조 위치**: `plan.mdc`의 "Docs 디렉토리 역할" 섹션에 정의

## 🔴 발견된 잠재적 문제점

### 1. Phase 번호 결정 기준의 모호성

**문제점**:
- `plan.mdc`의 "Phase 번호 결정 기준"에서 "관련된 기존 Phase를 찾아서 사용"이라고 명시되어 있으나, 관련 Phase를 찾는 기준이 모호함
- 예: "정규화 관련 문제 → Phase 4 관련"이라고 예시가 있으나, 실제로는 Phase 5에 정규화가 포함되어 있을 수 있음

**영향**:
- AI가 Phase 번호를 잘못 결정할 수 있음
- 문서가 잘못된 Phase에 생성될 수 있음

**해결 방안**:
- Phase 번호 결정 시 사용자에게 확인 요청하는 것을 더 강조
- 관련 Phase를 찾을 때 `plan/plan.md`나 `plan/tasks/`를 먼저 검색하도록 명시

### 2. History 기록의 중복 가능성

**문제점**:
- `agent.mdc`의 Planning Mode 케이스 2에서 `docs/` 문서 생성 시 History 기록을 요구
- `docs.mdc`에서도 History 기록을 요구
- 두 규칙이 중복되어 있으나, 실제로는 동일한 작업을 의미

**영향**:
- 중복 기록 가능성은 낮지만, 규칙이 중복되어 혼란을 줄 수 있음

**해결 방안**:
- `docs.mdc`에서 `agent.mdc`를 참조하도록 명시 (현재는 이미 참조하고 있음)

### 3. 동기화 승인 프로세스의 복잡성

**문제점**:
- `tasks.mdc`의 "Tasks 문서 수정 시" 프로세스에서:
  1. Tasks 문서 수정 전 승인
  2. 동기화 전 승인
  - 총 2번의 승인이 필요
- 이는 올바른 프로세스이지만, AI가 실수로 승인 없이 동기화할 수 있음

**영향**:
- 승인 없이 동기화가 수행될 수 있음

**해결 방안**:
- 동기화 승인 요청을 더 명확히 강조
- 체크리스트에 명시

### 4. 계획 파일이 없는 경우의 처리

**문제점**:
- `agent.mdc`의 Implementation Mode에서 "계획 파일이 없는 경우" Planning Mode로 전환하도록 명시
- 하지만 Planning Mode 케이스 1에서도 `plan/tasks/phase-{N}/phase-{N}.md` 파일이 없으면 생성하도록 명시
- 두 규칙이 일관되지만, Implementation Mode에서 Planning Mode로 전환할 때 승인 프로세스가 명확하지 않음

**영향**:
- Implementation Mode에서 계획 파일이 없을 때, Planning Mode로 전환하면서 `plan/plan.md`와 `plan/prd.md`를 수정해야 하는데, 이때 승인을 받아야 하는지 모호함

**해결 방안**:
- Implementation Mode에서 Planning Mode로 전환할 때도 `plan/plan.md`와 `plan/prd.md` 수정 전 승인을 받도록 명시

### 5. Test Mode의 History 기록 위치

**문제점**:
- `agent.mdc`의 Test Mode에서 "필요시 해당 Phase의 `plan/tasks/phase-{N}/phase-{N}.md` 파일의 History 섹션에 테스트 수행 내역 기록"이라고 명시
- "필요시"라는 표현이 모호함

**영향**:
- 언제 History를 기록해야 하는지 불명확

**해결 방안**:
- "필요시"를 구체화: "테스트 결과가 Phase 구현에 영향을 미치는 경우" 또는 "중요한 테스트 결과인 경우"로 명시

### 6. 파일 경로 관리의 중복 참조

**문제점**:
- `plan.mdc`에서 "파일 경로는 Tasks 문서에"라고 명시
- `tasks.mdc`에서도 "파일 경로: 생성/수정할 파일 명시 (전체 경로) - **필수**"라고 명시
- 두 규칙이 일관되지만, 중복되어 있음

**영향**:
- 규칙이 중복되어 있으나 실제 문제는 없음 (일관성 있음)

**해결 방안**:
- 현재 상태 유지 (명확성을 위해 중복 허용)

### 7. Phase/Sub-task 변경 시 프로세스의 복잡성

**문제점**:
- `plan.mdc`와 `tasks.mdc` 모두에서 Phase/Sub-task 변경 프로세스를 설명
- `tasks.mdc`에 더 상세한 프로세스가 있으나, `plan.mdc`에서도 간략히 설명
- 두 규칙이 일관되지만, 참조 관계가 명확하지 않음

**영향**:
- 프로세스를 찾을 때 어느 규칙 파일을 봐야 할지 혼란스러울 수 있음

**해결 방안**:
- `plan.mdc`에서 `tasks.mdc`의 상세 프로세스를 참조하도록 명시 (현재는 이미 참조하고 있음)

### 8. Execution Mode의 계획 파일 확인

**문제점**:
- `agent.mdc`의 Execution Mode에서 "계획 파일이 존재하는 경우" Implementation Mode로 전환하도록 명시
- 하지만 "계획 파일"이 무엇을 의미하는지 명확하지 않음 (`plan/tasks/phase-{N}/phase-{N}-{M}.md`인지, `plan/plan.md`인지)

**영향**:
- AI가 잘못된 파일을 확인할 수 있음

**해결 방안**:
- "계획 파일"을 구체적으로 명시: `plan/tasks/phase-{N}/phase-{N}-{M}.md` 파일

### 9. Test Mode의 테스트 결과 저장 위치

**문제점**:
- `agent.mdc`의 Test Mode에서 "테스트 결과를 `test_result/` 디렉토리에 저장"이라고 명시
- 하지만 `agent.mdc`의 "Test File Creation" 섹션에서는 "Results: Save output logs or results to `test_result/` directory"라고 명시
- 일관되지만, `test/` 폴더와 `test_result/` 폴더의 역할 구분이 명확하지 않음

**영향**:
- 테스트 파일과 테스트 결과를 어디에 저장해야 할지 혼란스러울 수 있음

**해결 방안**:
- `test/`: 테스트 스크립트 파일
- `test_result/`: 테스트 실행 결과 파일
- 역할을 명확히 구분

### 10. PRD의 변경 이력 vs Tasks의 History

**문제점**:
- `prd.mdc`에서 "변경 이력"을 `plan/prd.md` 문서 하단에 기록하도록 명시
- `tasks.mdc`에서 "History"를 `plan/tasks/phase-{N}/phase-{N}.md`에 기록하도록 명시
- 두 기록 방식이 다르지만, 이는 의도된 것일 수 있음

**영향**:
- 실제 문제는 없으나, 기록 위치가 다르다는 것을 인지해야 함

**해결 방안**:
- 현재 상태 유지 (각 문서의 특성에 맞는 기록 방식)

## ⚠️ 주의해야 할 부분

### 1. 승인 프로세스의 복잡성

**주의사항**:
- `plan/plan.md`, `plan/prd.md`, `plan/tasks/` 수정 시 모두 승인이 필요
- 동기화 시에도 승인이 필요
- 총 2번의 승인이 필요할 수 있음

**권장사항**:
- 승인 프로세스를 명확히 이해하고, 각 단계에서 승인을 요청

### 2. 문서 동기화의 범위

**주의사항**:
- Tasks 문서 수정 시 `plan/plan.md`와 `plan/prd.md`를 모두 확인해야 함
- Phase/Sub-task 변경 시 `docs/` 문서도 업데이트해야 함
- 동기화 범위가 넓어 실수할 가능성이 있음

**권장사항**:
- 동기화 체크리스트를 항상 확인
- 자동화 스크립트 고려 (향후)

### 3. Phase 번호 결정의 주의

**주의사항**:
- Phase 번호를 잘못 결정하면 모든 관련 문서를 수정해야 함
- Phase 번호 변경은 매우 복잡한 작업

**권장사항**:
- Phase 번호 결정 시 신중하게 결정
- 불명확한 경우 사용자에게 확인 요청

### 4. History 기록의 일관성

**주의사항**:
- 모든 History는 `plan/tasks/phase-{N}/phase-{N}.md`에 기록
- 하지만 PRD는 별도의 "변경 이력" 섹션에 기록
- 기록 위치가 다르므로 혼동하지 않도록 주의

**권장사항**:
- 각 문서의 History 기록 규칙을 명확히 이해

## 💡 개선 제안

### 1. Phase 번호 결정 기준 구체화

**제안**:
- Phase 번호 결정 시 다음 순서로 확인:
  1. 사용자가 명시한 경우: 그대로 사용
  2. `plan/plan.md`에서 관련 Phase 검색
  3. `plan/tasks/`에서 관련 Phase 검색
  4. 관련 Phase가 없으면 사용자에게 확인 요청

### 2. 동기화 프로세스 명확화

**제안**:
- 동기화 프로세스를 단계별로 명확히 구분:
  1. Tasks 문서 수정 (승인 필요)
  2. 동기화 승인 요청
  3. `plan/plan.md` 동기화 (승인 필요)
  4. `plan/prd.md` 동기화 (승인 필요)

### 3. Test Mode의 History 기록 기준 명확화

**제안**:
- "필요시"를 구체화:
  - 테스트 결과가 Phase 구현에 영향을 미치는 경우
  - 중요한 버그나 이슈를 발견한 경우
  - 테스트 결과가 문서화 가치가 있는 경우

### 4. Execution Mode의 계획 파일 명확화

**제안**:
- "계획 파일"을 구체적으로 명시:
  - `plan/tasks/phase-{N}/phase-{N}-{M}.md` 파일
  - 해당 Sub-task의 상세 구현 계획 파일

### 5. 테스트 파일/결과 저장 위치 명확화

**제안**:
- `test/`: 테스트 스크립트 파일 (`test/verify_*.py`, `test/test_*.py`)
- `test_result/`: 테스트 실행 결과 파일 (로그, 리포트 등)
- 역할을 명확히 구분하여 문서화

## ✅ 검증 결과 요약

### 전반적인 평가

**강점**:
1. ✅ Phase 번호 체계가 모든 규칙 파일에서 일관됨
2. ✅ History 기록 형식이 통일되어 있음
3. ✅ 승인 프로세스가 명확히 정의되어 있음
4. ✅ 문서 역할 구분이 명확함
5. ✅ 동기화 프로세스가 상세히 정의되어 있음

**개선 필요**:
1. ⚠️ Phase 번호 결정 기준의 모호성
2. ⚠️ 동기화 승인 프로세스의 복잡성
3. ⚠️ Test Mode의 History 기록 기준 모호성
4. ⚠️ Execution Mode의 계획 파일 정의 모호성
5. ⚠️ 테스트 파일/결과 저장 위치 구분 명확화 필요

### 프로젝트 진행 가능성

**결론**: ✅ **프로젝트 진행 가능**

**이유**:
- 규칙 파일들 간의 충돌이나 모순은 발견되지 않음
- 대부분의 규칙이 일관되고 명확함
- 발견된 문제점들은 주로 모호성 개선 사항이며, 프로젝트 진행을 막는 치명적인 문제는 아님
- 개선 제안을 반영하면 더욱 명확한 가이드라인이 될 것

**권장사항**:
1. 개선 제안 사항들을 점진적으로 반영
2. 프로젝트 진행 중 발견되는 문제점을 지속적으로 개선
3. 규칙 파일들을 주기적으로 검토하여 일관성 유지
